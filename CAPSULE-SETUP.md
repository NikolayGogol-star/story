# Капсула времени: запуск и проверка

Код подготовлен, но реальная отправка НЕ настроена и НЕ проверена. В `config.js` новый этап намеренно выключен (`CAPSULE_ENABLED: false`): существующий квест работает как раньше до завершения настройки. Никаких настоящих писем при разработке не отправлялось.

Серверный исходный код находится в локальной папке `capsule-server/` и в архиве `capsule-server.zip` в репозитории. Для настройки скачайте и распакуйте архив, затем выполняйте команды из этой папки. Архив не содержит секретов или данных читательницы.

## Бесплатный вариант без домена

Используются Cloudflare Workers + D1 + Cron + Turnstile и Gmail API. Аня вводит СВОЙ адрес (не обязательно Gmail); отдельный Gmail-аккаунт организатора выступает отправителем. Домен не покупается. Для этой небольшой личной задачи достаточно бесплатных квот; платные тарифы и биллинг не подключались. Официальные ограничения: [Gmail API](https://developers.google.com/workspace/gmail/api/reference/quota), [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/).

Resend не выбран: без собственного подтверждённого домена его тестовый отправитель позволяет писать только владельцу аккаунта. [Ограничение Resend](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).

## 1. Почтовый аккаунт и Google

Эти действия выполняет организатор вручную. Не присылайте секреты в чат и не публикуйте их в GitHub.

1. Используйте отдельный обычный Gmail-аккаунт для этой истории. В нём не должно быть личной переписки: разрешение `gmail.modify` позволяет работать с письмами этого аккаунта. Оно нужно для черновика, отправки, проверки неоднозначного результата и последующей очистки. Аккаунт не удалять до доставки и очистки.
2. Откройте [Google Cloud Console](https://console.cloud.google.com/), создайте проект для личной капсулы. В **APIs & Services → Library** включите **Gmail API**. Покупать Google Workspace не нужно.
3. В **Google Auth Platform** настройте Branding / Audience: приложение для личного использования, External, контактный адрес организатора. Укажите scope `https://www.googleapis.com/auth/gmail.modify` в Data Access. Для одного собственного аккаунта применяется исключение для личного использования; [официальное описание](https://support.google.com/cloud/answer/13464323?hl=en).
4. Переведите Audience / Publishing status в **In production** ДО получения окончательного refresh token. Режим Testing выдаёт Gmail refresh token только на 7 дней — такой токен НЕ подходит на год. [Сроки OAuth](https://developers.google.com/identity/protocols/oauth2#expiration).
5. Создайте OAuth client типа **Web application**. Authorized redirect URI: `https://developers.google.com/oauthplayground`. Сохраните Client ID и Client Secret вне репозитория.
6. Откройте [официальный OAuth Playground](https://developers.google.com/oauthplayground/). В настройках включите **Use your own OAuth credentials**, введите собственные Client ID / Secret. Access type — offline, Force prompt — consent. В Step 1 задайте scope `https://www.googleapis.com/auth/gmail.modify` и авторизуйтесь именно отдельным Gmail-отправителем. Авторизацию и подтверждение доступа выполните сами; не выдавайте доступ основному личному ящику.
7. В Step 2 нажмите **Exchange authorization code for tokens**. Сохраните **Refresh token** как секрет `GOOGLE_REFRESH_TOKEN`, а не краткосрочный Access token. Если refresh token отсутствует, заново запросите offline / consent для собственного OAuth client. Не используйте общие credentials Playground: годовое хранение зависит от вашего приложения.
8. `GMAIL_SENDER` далее должен точно совпадать с адресом авторизованного Gmail-аккаунта. Авторизация Ани в Google НЕ нужна.

Google может отозвать доступ при смене пароля, отзыве разрешения или долгом неиспользовании. Worker раз в неделю проверяет refresh token, чтобы избежать шестимесячного простоя; это не защищает от ручного отзыва. Раз в месяц проверяйте состояние, описанное ниже.

## 2. Cloudflare: D1 и Worker

Нужен бесплатный Cloudflare-аккаунт. Сайт остаётся на GitHub Pages. Ниже команды выполняются из папки `capsule-server/` в терминале с Node.js:

```sh
npx wrangler login
npx wrangler d1 create anna-future-letter
```

Из результата возьмите настоящий `database_id` и вставьте в `wrangler.jsonc` вместо пустой строки. ID базы не является секретом. В этом же файле укажите настоящий адрес отправителя в `GMAIL_SENDER`. `ALLOWED_ORIGIN` должен остаться `https://nikolaygogol-star.github.io` (без `/story/`).

```sh
npx wrangler d1 execute anna-future-letter --remote --file=schema.sql
```

Добавьте секреты интерактивно, по одной команде (Wrangler попросит значение; в код их не вставлять):

```sh
npx wrangler secret put GOOGLE_CLIENT_ID
npx wrangler secret put GOOGLE_CLIENT_SECRET
npx wrangler secret put GOOGLE_REFRESH_TOKEN
npx wrangler secret put LETTER_KEY
npx wrangler secret put ADMIN_TOKEN
npx wrangler secret put RATE_SALT
npx wrangler secret put TURNSTILE_SECRET
```

- `LETTER_KEY` — base64 ровно 32 случайных байтов для AES-256-GCM. Создать у себя: `python3 -c 'import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())'`.
- `ADMIN_TOKEN` — отдельная случайная строка не короче 32 символов. Создать: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`.
- `RATE_SALT` — ещё одна независимая случайная строка; используется для хеширования временных ограничителей запросов.
- Сохраните зашифрованную резервную копию `LETTER_KEY` и доступов в менеджере паролей. НЕ заменяйте ключ без миграции: сохранённое письмо станет нечитаемым.

## 3. Turnstile

В Cloudflare → Turnstile создайте widget с hostname `nikolaygogol-star.github.io`, режим Managed. Site key — публичный, Secret key — только Worker secret `TURNSTILE_SECRET`. Клиент запрашивает action `capsule`; сервер обязательно проверяет action и hostname. Настоящие ключи не заменяются тестовыми.

```sh
npx wrangler deploy
```

Запишите выданный реальный HTTPS-адрес `https://…workers.dev`. Cron `*/5 * * * *` работает каждые 5 минут, в UTC. В Cloudflare проверьте, что trigger действительно появился; изменение триггера может применяться не мгновенно.

## 4. Реальный тест отправки — ДО включения этапа

```sh
python3 admin.py test
python3 admin.py status
```

Helper спросит адрес Worker, секрет администратора скрытым вводом, ваш собственный email и искусственный тестовый текст. Реальная отправка произойдёт только после вашего `ДА`. Не вводите личное письмо Ани. Тест создаётся отдельной записью `is_test=1` с текущей датой и не меняет сроки настоящей капсулы.

Проверьте:

1. У тестовой записи `status: sent`, есть `sent_at`, `error_code: null`.
2. Тест действительно появился в вашем почтовом ящике; проверьте также «Спам».
3. В Sent Gmail-отправителя ровно одно тестовое сообщение, текст не обрезан.
4. После следующего Cron в `admin.py status` поле `health.cron_at` свежее, `health.oauth_ok: 1`.

`sent` означает, что Gmail API подтвердил отправку. Это не доказательство попадания во «Входящие»: получатель может иметь фильтры, переполненный ящик или неверный адрес. Мгновенную доставку в точную секунду гарантировать нельзя.

## 5. Подключить сайт

Только после успешного реального теста в `config.js`:

- `CAPSULE_API_URL` — ваш фактический HTTPS URL Worker без завершающего `/`.
- `CAPSULE_TURNSTILE_SITEKEY` — публичный Site key.
- `CAPSULE_ENABLED: true`.

Опубликуйте обновлённый `config.js` в существующий репозиторий; при этом поменяйте версию его URL в `index.html`, чтобы старый кеш не скрывал настройку. Другие пароли и `STORAGE_KEY` не меняйте. Никаких OAuth/API секретов в `config.js` быть не должно.

Пройдите на отдельном чистом браузерном профиле все этапы. Уже открытая IV глава на старых устройствах не блокируется — это сохранение прежнего прогресса, а не способ тестирования новой капсулы.

## Сроки и контроль 2027 года

- Открытие главы IV: **28.10.2026 00:00 Europe/Moscow** = **27.10.2026 21:00 UTC**. Подтверждается сервером, не часами телефона.
- Отправка письма: **28.10.2027 10:00 Europe/Moscow** = **28.10.2027 07:00 UTC**. Cron проверяет `delivery_at <= now`, поэтому задержанный/пропущенный запуск догоняет отправку и после этой даты.
- После настоящего сохранения проверьте в `admin.py status`: `is_test: 0`, `status: pending`, `delivery_at: 1824706800000` (07:00 UTC). До срока Gmail-письмо и даже Gmail-черновик не создаются.
- Раз в месяц проверяйте Cron / OAuth через `admin.py status`, доступность бесплатных аккаунтов и актуальные квоты. Проведите тест на свой адрес в октябре 2027 года до дня рождения. Не меняйте дату настоящей записи ради теста.
- Ошибки приводят к `failed` и автоматическим повторным попыткам с увеличением интервала до суток. Gmail-черновик сохраняет один ID; повторно используется тот же черновик. Если он уже отправлен, Gmail его удаляет, и Worker сверяет Sent по стабильному Message-ID. Новый черновик вместо исчезнувшего автоматически НЕ создаётся: это защищает от двойного письма. `draft_missing_needs_review` требует проверки организатором (не создавайте вручную вторую капсулу).
- Не удаляйте Worker, D1, Cron, Gmail-аккаунт и OAuth-приложение до отправки и очистки. Годовая работа зависит от этих сервисов; её невозможно доказать одним сегодняшним тестом.

## Конфиденциальность и удаление

Адрес и текст передаются только HTTPS POST, шифруются AES-256-GCM до записи в D1. В логах — только случайный ID и код ошибки. Страница администратора не возвращает адрес или текст; доступ защищён Bearer-секретом, не скрытым URL.

Аня может нажать «Удалить письмо до отправки» и подтвердить действие. Удаление требует случайного ключа-квитанции, сохранённого на её устройстве, и стирает зашифрованные адрес и текст. При потере устройства необходимо обратиться к организатору: идентификатор и `created_at` можно сопоставить в D1, а затем организатор вручную выполняет удаление конкретной записи. Не удаляйте запись со статусом `sending`, пока не закончится текущая попытка. Квитанцию нельзя публиковать или пересылать: она даёт доступ к удалению, но не чтению письма.

Вернуться к капсуле после финала можно кнопкой-конвертом в оглавлении. Если до удаления уже был создан Gmail-черновик при неудачной отправке, Cron также удалит его. При аварии между созданием черновика и записью его ID Worker пытается убрать незакреплённый черновик; если и эта очистка не удалась, код `capsule_orphan_draft_cleanup_pending` требует ручной проверки Drafts отдельного отправителя. Не отправляйте такие черновики вручную.

Черновик по умолчанию хранится только в sessionStorage вкладки (переживает перезагрузку). Для сохранения после закрытия браузера есть отдельная необязательная галочка. Это локальная незашифрованная копия: на общем устройстве не включать. После подтверждения сервером черновик и поля очищаются. В прогрессе остаются только этап и случайная квитанция.

Через 7 дней после подтверждения отправки Worker стирает содержимое из D1 и перемещает свою отправленную Gmail-копию в корзину (Gmail очищает её по своим правилам). Если очистка Gmail не удалась, последующие Cron повторяют её. У почтового получателя остаётся его копия. Резервные копии/Time Travel D1 и сервисные копии Google имеют собственные сроки хранения: удаление из рабочей таблицы не означает мгновенное стирание всех резервных носителей.

## Что доступ не защищает

Существующая глава IV и кодовые фразы уже находятся в публичном `content.js` / `config.js` GitHub Pages. Новая логика закрывает обычную навигацию до даты, но НЕ скрывает текст от просмотра исходников и НЕ является защитой от изменения localStorage. Дата сервера применяется к штатному сценарию; настоящую секретность финала потребовал бы отдельный перенос текста на сервер (здесь это намеренно не сделано).

## Проверки без аккаунтов

```sh
node --test worker.test.mjs
node preview.mjs
```

Node.js 24+ нужен для тестовой SQLite. Preview: `http://127.0.0.1:8028/` — только локальный эмулятор, никакой почты, настоящих OAuth-секретов или настоящего Turnstile. Он явно помечен, база в памяти пропадает при остановке. Не вводите личных данных. Служебные локальные `/__preview/fail` и `/__preview/open` имитируют ошибку сохранения и дату открытия; их нет в рабочем Worker.

Подтверждено автоматическими тестами: согласие, email, CORS, серверная проверка Turnstile, лимит запросов, шифрование, повтор сохранения, даты до/после московской полуночи, отсутствие отправки раньше 2027 года, параллельные Cron, временный сбой, сбой записи после отправки без дубля, удаление и очистка. Gmail и Cloudflare пока эмулировались: требуются отдельные реальные развёртывание, авторизация и тест из раздела 4.
